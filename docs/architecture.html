Technical design

Tech stack & architecture

How On-Track is built: one Next.js app (local, optional Vercel), Postgres, Claude Haiku 5.5 for reading contracts and invoices, PayPal sandbox for money, and Bryntum Scheduler and Calendar for the views. Requirements IDs (R1…) refer to the PRD.

Version: 0.1 Date: Oct 12, 2026 Status: Draft

1. Design principles

AI proposes, code decides

The AI produces verdicts and proposals. Whether money moves is decided by a plain TypeScript guardrail function the AI cannot bypass (R15–R17).

PayPal is the source of truth

"Paid" only becomes true when a verified PayPal webhook says so, never because the UI or the agent assumed it.

Every money call is idempotent

Payout batch IDs and invoice numbers derive from our own record IDs, so a retry can never pay twice (R16).

One app, few moving parts

Solo builder, 35 hours. One deployable, one database, no queues. Background work runs inside request handlers or webhook handlers.

5. State machines

Assignment

stateDiagram-v2
  [*] --> scheduled
  scheduled --> submitted: proof or invoice uploaded
  submitted --> verified: checklist complete or invoice matches
  submitted --> held: checklist item missing or invoice mismatch
  held --> submitted: new submission
  held --> verified: user override with reason
  verified --> awaiting_approval: payout created
  awaiting_approval --> scheduled: staff member approves
  awaiting_approval --> held: rejected with reason
  awaiting_approval --> awaiting_approval: amount or date edited (R26)
  scheduled --> awaiting_approval: amount or date edited (R26)
  scheduled --> payout_sent: payout date reached or Send now
  payout_sent --> paid: webhook SUCCEEDED, or Check status / daily run
  payout_sent --> payout_failed: webhook or status check FAILED or UNCLAIMED
  payout_failed --> awaiting_approval: retry
  paid --> [*]

Client invoice

stateDiagram-v2
  [*] --> draft
  draft --> sent: send via PayPal
  sent --> paid: webhook INVOICING.INVOICE.PAID
  sent --> sent: due date changed (R19)
  paid --> [*]

The deposit invoice reaching paid sets CAMPAIGN.deposit_cleared = true. That flag is the payout lock in R15.

7. AI design

Two AI jobs are required for v1. Post verification is a human checklist; AI only offers an optional pre-check. Each AI job is a single Claude Haiku 5.5 call using structured outputs (output_config.format) validated by Zod. Forced tool calls are avoided because they return an error on Sonnet 5.5, which would break the fallback. The agent (a "Should") is one structured-output call too.

JobInputOutputReqs
Required for v1
ContractExtractorContract PDFClient, total fee, deposit %, due dates, deliverables, per-creator fee and due date. Each field has a source quote from the PDF.R1
InvoiceMatcherInvoice PDF or image, assignment contract termsExtracted payee, amount, currency, deliverable, with a confidence. The comparison against the contract is done in code, so a mismatch is never left to the model.R11
Optional ("Should")
PostPreCheckPost screenshot, assignment briefSuggested tick per checklist item (brand tag, hashtags, posting date) with a reason. Pre-fills the checklist; staff confirm.R24
Agent plannerStaff instruction + this campaign's payouts (payee, amount, status, verification, deposit)Payout ids to approve + a one-line summary. Each id is dry-run through canPay() and shown with its result; a person approvesR22

Example: InvoiceMatcher

// Haiku extracts (structured output):
{ "payee": "Daniel Lim", "amount": 1200.00, "currency": "USD",
  "deliverable": "2 × 30s product video edits", "confidence": 0.95 }

// Code compares against the contract:
{ "match": false,
  "mismatches": [ { "field": "amount", "contracted": 1000.00, "invoiced": 1200.00 } ] }

The model only reads the invoice. Deciding whether it matches is plain code, so the model cannot approve a wrong amount.

Cost

A one-page invoice or a short contract is a few thousand input tokens. At Haiku 5.5 rates ($0.10 / $0.50 per million), each check costs a small fraction of a cent, and all development, eval runs and the demo together should stay well under $1.

Agent

The agent has no tools. It gets the staff instruction (quoted as data, not rules) and a JSON list of the campaign's payouts, and returns { payoutIds, summary }. Code drops any id that isn't in the list, runs canPay() on each as if approved now, and shows the result next to a checkbox. Nothing is approved until a person clicks. The R19 balance-date proposal is plain code (balanceProposal()), not the agent.

Evaluation

eval/ holds 10 freelancer invoices (5 correct, 5 mismatched) and 3 sample contracts, each with the expected result. Add post screenshots only if PostPreCheck is built. npm run eval prints accuracy against the PRD targets. Run it after every prompt change.

8. Payment guardrails

One pure function, unit-tested. It runs when a payout is queued, when it is approved, and again at send time, because the situation can change in between (for example, a payout scheduled before a refund).

type PayDecision =
  | { kind: "allow" }
  | { kind: "needs_approval"; reason: string }
  | { kind: "deny"; reason: string };

export function canPay(a: Assignment, c: Campaign, v: Verification | null, p: Payout): PayDecision {
  if (!c.depositCleared)          return { kind: "deny", reason: "Client deposit not received" };   // R15
  if (a.status === "paid" || p.status === "payout_sent")
                                  return { kind: "deny", reason: "Already paid" };                  // R16
  if (!v?.pass)                   return { kind: "deny", reason: "Work not verified" };
  if (p.amount > a.fee)           return { kind: "deny", reason: "Exceeds contracted fee" };        // R16
  if (!p.approvedBy)              return { kind: "needs_approval", reason: "Waiting for approval" }; // R17
  return { kind: "allow" };
}

Edits (R26) go through the saveEdit Server Action and editPayout(), which rejects an amount above the contract fee or a date before today, requires a reason, writes an audit event with before and after values, and moves a scheduled payout back to awaiting_approval by clearing approved_by. A payout_sent or paid payout can't be edited.

Unit tests cover every branch. Database writes for a payout run in a transaction that re-reads the assignment row with SELECT … FOR UPDATE, so two clicks can't both pass the "already paid" check.

Webhook events subscribed

EventEffect
INVOICING.INVOICE.PAIDInvoice → paid. If deposit, set deposit_cleared.
PAYMENT.PAYOUTS-ITEM.SUCCEEDEDPayout and assignment → paid. Event turns green.
PAYMENT.PAYOUTS-ITEM.FAILED, …UNCLAIMEDPayout → payout_failed with PayPal's reason; the queue shows Retry payout. Only the attempt in flight is settled; late events from an earlier attempt are ignored.

Webhook handling is idempotent: store each PayPal event ID and skip it if already processed.

10. Bryntum integration

Mapping our data to Bryntum

Bryntum conceptComes from
Resource (Scheduler row)Each creator on the campaign, plus one "Client" row
Event: post due / deliverable dueASSIGNMENT.due_date, colour by creator type and status
Event: client invoiceCLIENT_INVOICE.due_date on the Client row
Event: payoutPAYOUT.scheduled_for on the creator's row. Shown as "awaiting approval", "scheduled" or "sent" by status
Event colourDerived from status: overdue or flagged → red; paid → green (see PRD colour key)

Sharing data between the two views

  • Both views render from the same server data (loadTimeline() → toTimeline()), re-fetched every 3 s and after every drop, so a change in one shows in the other within seconds (R14).
  • Rows are ordered influencers first, then freelancers, then by name, so refreshes never reorder them.
  • Each widget is unmounted while its page is hidden (useShown), because Next.js keeps visited pages mounted for Back/Forward.

Drag handling

Only post and deliverable events are draggable. Invoice and payout events are read-only, because their dates change only through the flow in 6.4. A drop is saved through the moveAssignment Server Action. If the server rejects it, the event snaps back.

Environment variables

PAYPAL_CLIENT_ID=

PAYPAL_WEBHOOK_ID=
CRON_SECRET=                     # protects /api/payouts/run-due

Never commit .env. The repo must be public for submission, so add .env* to .gitignore before the first commit and check git status before every push.

Run and deploy

  1. Local: make up (Postgres in Docker), npm run db:push, npm run db:seed:roster, npm run dev. Full steps in the README.
  2. Webhooks: cloudflared tunnel --url http://localhost:3000, register <tunnel>/api/webhooks/paypal in the PayPal developer dashboard and copy the webhook ID into PAYPAL_WEBHOOK_ID.
  3. A "Reset demo" button (DEMO_RESET=1) reseeds, so judges and the video always start clean.
  4. Optional hosting on Vercel: hosted Postgres (e.g. Neon), Vercel Cron calling /api/payouts/run-due with CRON_SECRET, and a second webhook for the Vercel URL.
